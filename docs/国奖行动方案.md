## 一、方向定稿

不再纠结单图还是多图，团队明确以**单图生成**为核心，同时把老师要求的多模态三维生成做成创新亮点。整体是一个"多引擎单图生成 + 多模态条件 + 可观测性提示 + 移动端闭环"的完整系统。

一句话主线：**上传一张瓷器照片，可选择多个引擎分别生成、横向对比，也可以叠加文字描述做多模态生成，系统标出哪些是可见区域、哪些是推断区域。**

## 二、五个引擎/方法的真实定位（基于实测和官方数据）

| 引擎 | 输入条件 | 运行位置 | 显存门槛与状态 | 在产品里的角色 |
|---|---|---|---|---|
| TripoSR | 单图 | 本地 | 已跑通，约 25 秒 | 快速预览，离线兜底，已接入 |
| SF3D | 单图 | 本地 | 峰值 6.2GB，约 18 秒；**本轮按队长要求暂停** | 备用快速预览，带 UV 和材质，后续再定 |
| InstantMesh | 单图 | 云端 ZeroGPU | 本地 large 需 24GB（8GB 无方案）；匿名 GPU 失败，**待 HF token** | 高质量单图对照 |
| Meshroom | 多图（2–40 张） | 本地 | 8GB 卡用 2K 贴图、downscale=4 可跑，约 8 分钟；**已跑通接入** | 多图精细复原，真实几何+实拍贴图 |
| Hunyuan3D 2.x mini | **图+文多模态** | 本地（低显存模式） | **形状已跑通：峰值 4.08GB、约 30 秒、52–55 万面、几何水密**（UV 接缝复制是索引口径，非真洞）；完整贴图 16GB 需另装 CUDA 编译 | 多模态生成，创新担当 |

关键事实说明：

1. **单图三引擎都能用，而且应该都用**。产品做成"同一张图、多引擎并行生成、结果横向对比"，这就是 benchmark 的产品化，工程选型叙事比单押一个模型强得多；
2. **InstantMesh 不是不用，是本地 8GB 物理上跑不动、匿名云端又被 ZeroGPU 限制**。可行路径是配置 HF token 走账号配额，或自租 24GB 实例；本地 TripoSR 保底，答辩不依赖它；
3. **Meshroom 是当前唯一已完整跑通并接入产品的精细重建路径**。它需要多张环绕照片，产出真实几何和实拍贴图，面数约为单图模型的 10 倍，定位为"多图精细模式"，与单图"快速预览"形成档位区分；
4. **多模态三维生成由 Hunyuan3D 承担**。它原生支持图像和文本条件，官方 API Server 就有 Image/Text to 3D，形状生成只要 6GB，8GB 卡配合 low_vram_mode 和 mini 版本可以本地跑。这是真正贴合老师意图的"多模态三维生成"，不是文字检索的外围功能。

## 三、产品功能架构

### 3.1 多引擎单图生成（核心）

- 同一张照片，可勾选 TripoSR、SF3D、InstantMesh 中的一个或多个，分别生成；
- 结果页支持同屏切换、并排对比，展示每个引擎的面数、耗时、文件大小；
- 这些数据直接来自 benchmark，产品里能看到真实的选型依据，而不是报告里说说。

### 3.2 多模态三维生成（创新亮点，机制已核实）

> 2026-11-25 更新：本节的多模态路线**已暂缓**，实际决定、核实过的 API 选型和不做的原因见 `docs/未完成清单与分工_2026-11-22.md` 第四章。以下内容作为背景保留，不再按此推进。

读源码确认了一个必须讲清楚的事实：Hunyuan3D 的形状模型（DiT）条件端只有图像编码器（DINOv2），**接口本身不直接接收文本**。官方对文字的处理是先用文生图模型把文字转成图，再走"图→形状"。所以产品按三种真实路径做：

- **图像 → 三维**：照片去背景后直接进形状管线，这是主路径；
- **文本 → 三维**：输入文字描述（如"器身扁圆、两侧有耳、青花纹饰"），先文生图再生成形状；
- **图 + 文（探索项）**：若要让文字真正影响同一张图的生成，需要把文本编码注入条件端做自定义改造，这是有工作量的探索，做成了是加分，做不成就如实定位为前两种。

诚实边界：系统确实能接收图像和文本两种模态输入，但不夸大成"形状模型原生支持图+文联合条件"；所有效果以本地实测和对照记录为准。

**文生图这一环的工程选型（本轮实测后补充）**：官方默认的 `HunyuanDiT-v1.1-Diffusers-Distilled` 是公开模型（非 gated），但全套权重约 **13.8GB**（两个 text encoder 约 7.7GB、transformer 5.8GB、VAE 0.3GB），按当前网络速度（约 200–660KB/s）下载要数小时到十几小时，且 fp16 常驻显存压力大。落地上有三个可选方向，待团队拍板：① 网络好时后台慢慢下完整官方模型，质量和中文最稳，文生图与形状两个管线分步加载、用完即释放，8GB 显存可串行跑；② 用更轻量的开源文生图（如 SD1.5/SD-Turbo 蒸馏版，单 checkpoint 约 2GB），中文 prompt 先翻译再生成，代价是题材贴合度和中文质量；③ 文生图走云端 API、形状仍本地，零额外本地权重，但要配 API key 且需说明开源边界。当前先不阻塞主线，权重就绪前"文本→三维"入口预留但不宣称已完成。

### 3.3 可观测性提示（已有，保留）

- 现有 `uncertainty.py` 的启发式热力图继续用，统一叫**可观测性/推断区域提示**；
- 代码注释已明确这不是概率置信度，答辩不说是 AI 置信度或精度证明。

## 六、风险清单

1. **InstantMesh 双重受限**：本地 8GB 物理跑不动，匿名 ZeroGPU 又被配额和共享池限制，当前阻塞于 HF token。不硬磕，本地 TripoSR + Meshroom 保底，答辩不依赖它；
